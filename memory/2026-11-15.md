### 排查中抓到的真 bug（BMP 解码器）
- **bottom-up 行写入被覆盖**：行分配 `gray[row] = make(...)` 在循环内按 **row** 索引重分配，而写入用 **y（转置行）**——bottom-up 时 row=0 写 gray[1]、row=1 重置 gray[1]，数据丢失（top-down 时 row==y 侥幸正确）。修法：分配移到写入循环前。dump 定位过程：字节正确 → 循环内 gray 正确 → 循环后被重置 → 锁定分配时序。

### 关键边界（如实记录）
- **24-bit color BMP 无法走 CLI 直喂**：3 字节/像素，290px 截图 253KB → base64 337KB 超 CreateProcess 硬上限（WinError 206 实测，比 MAX_B64=30000 更严）；fit 缩放后 56px 仅 1.9px/module 低于采样下限。彩色像素覆盖由 RGB screenshot（PNG 路径）case 承担；真实剪贴板格式 1-bit/8-bit BMP 已覆盖
- JPEG/GIF/TIFF/WebP 不做 MoonBit 侧解码（JPEG DCT 工作量巨大且所有格式可先经调用方转 PNG/灰度）——**无损传输的本质是像素无损，与截图容器格式无关**
- **MoonBit js 后端 `Char::to_string()` 返回码点数字**（'f' → "102"）——dump 显示层误导排查约 30 分钟；native 正常。已并入 moonbit-language-pitfalls

## issue #2527 官方回复：根因是应用层 bug，已修复并启用浏览器内引擎（定性修正）

**官方（peter-jerry-ye）源级诊断完全正确**：js 引擎返回 "52565457" 不是工具链问题，而是 `web_bytes_to_hex` 的 **hex 格式化 bug**——`digits[index]` 在 js 后端返回 **UTF-16 码点 Int**（'4'→52），`.to_string()` 输出数字字符串。"Hi" 的正确 hex "4869" 的码点拼接恰为 "52565457"，字节数不变 → **静默错值**。

**我的定性错误复盘**：
- 之前判「native 对 js 错」——实际对比的是**两条不同代码路径**：native CLI 走 `bytes_to_display/hex2`（match 字面量实现，正确），js 引擎走 `web_bytes_to_hex`（digits 索引，错误）
- 诊断 dump 自己也用了 `digits[i].to_string()` 拼接 → **诊断工具与被测代码共享同一 bug**（用坏尺子量东西），dump 的 "102102"（'f' 的码点）被误读为「字节内容异常」
- 「foreign_library 构建上下文差异」的定性被推翻——应用层一行修复

**修复**：`web_hex_digit` 整数 `match` 字面量（跨后端稳定的字符串字面量），替代索引查表。修复后：
- repro 脚本：`native: OK | js artifact: OK`，not reproduced（exit 0）
- **js 引擎多格式实测**：PNG ✓ BMP ✓（hex 与期望逐字节一致）；GIF/TIFF/JPEG/WebP 按设计拒收（需调用方先转）
- **浏览器内引擎已启用**：camera.html 解码链改为 浏览器内引擎（`/wasmapi.js`，MoonBit js 产物 ESM）→ server API → jsQR 兜底；server.js 增加 `/wasmapi.js` 路由（HTTP 200 实测）

**教训入库**：
1. **诊断探针与被测代码共享组件时，探针输出不可信**——先验证探针本身
2. **「同代码不同结果」先查代码路径是否真同**——两条路径各自正确也会呈现差异
3. `String[i]` 在 js 后端返回码点 Int（native 亦然，是统一 API 行为）；跨后端代码避免 `s[i].to_string()`，用 match 字面量或显式 Char 转换
