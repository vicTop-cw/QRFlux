## T0.5 图像入口解码 — 补全「截图 → 矩阵」断点

**触发**：用户点出项目真实场景断点——「远端电脑用程序生成二维码图片 → 截图传过来 → 本地解码」，但当前解码器只吃干净模块矩阵，**图像 → 矩阵的入口层完全缺失**，初审必挂。

**侦察实况（实测取证）**：
- `decode_qr(matrix : FixedArray[FixedArray[Int32]])` 入参为 0/1 整数矩阵；`decoder.mbt` 全文 grep `finder 定位/二值化/采样/threshold` **零命中**，头注释自陈 "no geometric distortion"
- 全仓 6 个 image 测试文件测的都是**图片格式正确性**（PNG header/IDAT 结构），无一条「从图片解码」
- `camera.html` 摄像头扫码靠外部 **jsQR**（CDN）；交叉验证 165/165 靠 Python **zxing-cpp**
- 结论：编码侧齐装满员，解码侧只有「干净矩阵」入口 → 断点实锤

## 途中定位并修掉的三个真 bug

1. **采样公式半数 module 偏移**（E2E 全红根因）：`(i - 3.5)` 应为 `(i - 3.0)`——module 索引 i 的中心坐标为 `i+0.5`，相对 finder 中心 3.5 的位移是 `i-3`。修正后 42 个错位 module → 0。
2. **`unit = r3/3.0` 使 r3 比例检查恒真**：unit 用 r3 自身推导，导致 1:1:5:1:1 中心过宽的图案也能通过比例闸。改用 `total/7`（全 7 module 宽度）估计，比例闸恢复效力（白盒反例测试这才真正拒绝）。
3. **测试里 `FixedArray::make(3, FixedArray::make(3,0))` 内层数组被三行共享**：赋初值时互相覆盖，导致旋转测试断言值全错。修法：逐行 `FixedArray::make(3, 0)` 重新分配（项目既有惯例）。

## 已知边界（如实登记，未收口）

- **不含透视校正**：仿射模型仅覆盖缩放/平移/旋转（90° 倍数）与轻微形变；强透视（斜拍）需后补 homography
- **亮度极端不均**未处理：全局 Otsu 在局部阴影/反光下会失效，需自适应局部阈值
- **PNG 文件直读未做**：像素需调用方（浏览器 canvas / Python PIL）提取后传入；项目 PNG 用 stored blocks，自写 inflate 读回是后续可选项

## Push 上线 + wasm/js 导出尝试（2026-11-13 续）

**push 上线**：109 个 commit 推上 GitHub（`1d1755a..9d72af6`）。踩坑：Windows 凭证助手（credential.helper=manager）在 HTTPS 推送时会弹窗导致命令挂起；改走 SSH（`git@github.com:vicTop-cw/QRFlux.git` + `GIT_SSH_COMMAND` 显式指定 `-i C:/Users/victo/.ssh/id_ed25519` 与 `UserKnownHostsFile`，因 Loomy 会话 HOME 重定向导致 ssh 找不到真实用户的 key/known_hosts）。远端回读确认 `9d72af6`。

**wasm/js 导出（`src/wasmapi`，foreign_library + #export_name）**：
- 机制查证：MoonBit 导出需 `pkgtype(kind: "foreign_library")` + `#export_name("sym")`（或 moon.pkg 的 `link.<backend>.exports`）；字符串跨边界需 **wasm-gc + use-js-builtin-string**（Wasm MVP 下 String 无稳定 ABI）
- wasm-gc 产物：3 个符号导出成功（`WebAssembly.Module.exports` 实测），但实例化需要 host 提供 75 个 `(global (ref extern))` 的 js_string_constant 导入；JS API 的 nullable externref/anyref 与 non-null `(ref extern)` 类型不匹配 → **无法简单实例化**
- js 产物：3 个符号以 ESM 导出成功（`export {... as qrflux_encode_qr, ...}` + d.ts），node 可 import 并调用
- **但 js 引擎长输入返回错误结果**（`ok:true` + 22 字节乱码，native CLI 同一 PNG 正确）——静默错值，**不交付**

**排查记录（逐步排除，未定位到最终根因）**：
| 假设 | 实验 | 结果 |
|---|---|---|
| release 优化问题 | debug 构建对照 | 同样错 ✗ |
| base64（core）bug | 换自研 base64 实现 | 同样错 ✗ |
| 迭代器 bug | 改索引访问 | 同样错 ✗ |
| 字符串传递损坏 | echo 码点 + 全长遍历统计（14784 字符 invalid=0 upper=4327 lower=486） | JS/MB 完全一致 ✓ |
| Buffer 大量写入 | 11088 字节模式写入逐字节校验 | bad=0 ✓ |
| 位运算/比较 | 内联最小 base64（无 helper/无 Buffer/无跨包） | bytes=137,80,78 ✓ |
| 跨包调用 | `@qr.base64_decode("iVBO")` 短输入 | 正确 ✓ |
| **跨包 + 长字符串** | 唯一剩余差异 | **未能直接验证**（诊断函数只做包内遍历正常） |

**结论**：隔离到「经 foreign_library 构建、跨包传递长字符串参数」的组合，属构建上下文相关的工具链异常（普通构建/`moon test`/native 全部正确）。**已收敛**：`src/wasmapi` 保留（导出机制验证价值 + 3 符号可复现），头注释写明状态；前端继续走本地 server API。

**顺带修掉的真 bug**：`web/server.js` 原用 `execSync` 拼字符串调用 CLI，Windows 下经 cmd.exe 有 ~8191 字符命令线上限 → 19012 字符的 PNG base64 **必然失败**（此前的 28000 上限设置是错的）。改用 `spawnSync('moon', ['run','cmd/main','--', ...argv])` 直接走 CreateProcess，上限提到的 30000 并附明确错误提示；改造后实测 19012 字符负载 → HTTP 200 → 「Server API fix test」精确还原。

**清理**：删除自研 base64（未验证即不用）、所有 `_tmp_*` 诊断脚本与临时测试。
