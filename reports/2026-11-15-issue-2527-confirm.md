Confirmed — your source-level diagnosis was exactly right, and it turned out to be an application bug rather than a toolchain issue.

`digits[index]` on the js backend is a UTF-16 code unit (`Int`), so `.to_string()` printed its numeric value (`"f"` → `"102"`). The reported payload `52565457` was the code-unit concatenation of the **correct** hex `4869` for `"Hi"` — the decoded bytes were fine the whole time; only the formatter was broken.

Fixed in https://github.com/vicTop-cw/QRFlux/commit/113c968 by replacing the indexed lookup with an integer `match` (backend-stable string literals). After the fix:

- `node scripts/repro_wasm_export_issue.cjs` → `native: OK | js artifact: OK`, exit 0 (not reproduced)
- The js artifact now decodes PNG and BMP screenshots end-to-end with correct payloads and is wired into the web frontend as the primary in-browser decoder (local server API and jsQR as fallbacks)

Two side notes from the investigation:

1. My earlier "native correct / js wrong" framing was misleading — the two paths used *different* formatters (`bytes_to_display`/`hex2` with a match on native vs. `web_bytes_to_hex` with the indexed lookup on js), so each was "correct for its own code" while disagreeing. My debugging dump also used the same indexed lookup, which contaminated the diagnostics — a broken ruler measuring itself.
2. For what it's worth, `String[i]` yielding a code-unit `Int` (rather than a `Char`) on the js backend is a subtle trap for exactly this pattern; a doc note or lint could help others.

Thanks for the quick and precise diagnosis — no need to reopen since the fix is on our side.
